# Zed Terminal Memory

This file records durable project context for the standalone `zed_terminal` app.

## Product Direction

- Build a standalone terminal application that feels like a product, not a demo.
- Preserve the official Zed terminal rendering and component style.
- Iterate primarily by composing Zed crates from a new `crates/zed_terminal` binary crate.
- Keep changes to existing Zed crates minimal and only expose APIs when composition requires it.
- Use Windows Terminal as the reference for tab, split, settings, and shortcut expectations.

## Current Architecture

- `crates/zed_terminal` is a standalone binary crate with binary name `zed-terminal`.
- The app initializes a lightweight subset of Zed services and opens one GPUI window.
- `workspace::Workspace` provides the center pane, tab strip, split panes, focus, and item lifecycle.
- `terminal_view::TerminalPanel::add_center_terminal` creates terminal tabs backed by Zed's existing terminal stack.
- `terminal_view::TerminalPanel::add_center_terminal_with_custom_title` is the standalone startup path for titled tabs and initializes the same `TerminalView` custom title state used by official Zed terminal tab renaming.
- `terminal_view::TerminalPanel::split_center_terminal_with_custom_title` is the narrow standalone startup path for configured split panes and still creates the same official `TerminalView` before handing it to `workspace::Workspace::split_item`.
- `project::Project::create_terminal_shell_with_shell` is the standalone startup path for configured shell-only tabs and keeps them on the same normal terminal shell lifecycle as Zed terminals.
- `terminal`, `terminal_view`, `workspace`, `command_palette`, `search`, `ui`, settings, themes, and keymaps are reused instead of forked.
- Standalone command palette filtering uses `command_palette_hooks::CommandPaletteFilter`; it hides broad Zed/editor/project namespaces and explicitly re-shows known terminal product actions.
- Standalone terminal buffer search initializes Zed's `search::buffer_search` surface, registers `workspace::PaneSearchBarCallbacks`, and mounts `search::BufferSearchBar` into each terminal pane toolbar before `terminal_view` creates terminal panes.
- `crates/paths` exposes custom data/config directory hooks so `zed-terminal` can be a standalone product without changing normal Zed paths.
- By default, `zed-terminal` uses independent config/data/log roots named `Zed Terminal` / `zed-terminal`, with `--user-data-dir` and `--config-dir` overrides for smoke tests and portable launches.
- The default terminal keymap lives at `assets/keymaps/zed-terminal.json` and is loaded through `settings::KeymapFile` before user keymap overrides.
- Standalone startup layout is configured by `terminal.json` in the active terminal config directory. It is intentionally separate from Zed's normal `settings.json`, so Zed settings can keep owning themes, fonts, and terminal renderer behavior.
- Standalone CLI handling is split into explicit `PrintPaths`, `ListProfiles`, `DescribeProfile`, `DescribeStartup`, `SetDefaultProfile`, `ClearDefaultProfile`, `PrintStartupLayout`, `ValidateStartupConfig`, `PrintStartupConfigSchema`, `PrintDefaultKeymap`, `InitConfig`, `Doctor`, `ValidateKeymap`, and `Launch` modes so discovery, configuration edits, initialization, diagnostics, and validation commands do not accidentally validate unrelated startup state or launch terminal windows.

## Rendering Parity Requirements

The app must keep these startup steps aligned with Zed before terminal views are created:

- `gpui_platform::application().with_assets(Assets)`
- `Assets.load_fonts(cx)` for embedded `.ZedMono` and `.ZedSans`
- `theme_settings::init(theme::LoadThemes::All(Box::new(Assets)), cx)`
- load and watch user themes from `paths::themes_dir()`
- initialize and watch settings files before first terminal render
- synchronize `WorkspaceSettings::text_rendering_mode`
- apply the active theme's window background appearance

Skipping these steps breaks font metrics and theme colors, which makes the standalone terminal diverge from the official Zed terminal.

## Current Decisions

- The standalone app no longer shares normal Zed config/data paths by default.
- The settings and keymap actions open terminal-specific `settings.json` and `keymap.json` under the active terminal config directory.
- Product support entries open the config, data, logs, and themes directories plus the current log file using GPUI's platform `open_with_system` API.
- Support directory actions reuse the existing `paths::*` roots and do not touch terminal rendering, input, PTY, startup layout, keymap defaults, or visual styling.
- The log file action reuses `terminal_log_file()`, ensures the parent logs directory exists, creates a missing log file in append mode, and never truncates existing log content.
- `ctrl-j` is intentionally left unbound in the standalone default keymap so the terminal receives LF input.
- `--update-startup` edits only the root startup layout's initial tab fields: `working_directory`, `command`, `title`, and `shell`. Root `env`, root nested `tabs`, profile startup fields, profile env, and profile discovery metadata stay on their separate command surfaces.
- `--update-profile` remains scoped to profile discovery metadata (`display_name`, `description`, `icon`, and `color`); profile initial startup fields are managed by the separate `--update-profile-startup` command.
- `--update-profile-startup` edits only a profile's initial tab fields: `working_directory`, `command`, `title`, and `shell`. Profile environment variables are managed by the separate `--update-profile-env` command, and nested `tabs` remain separate future work.
- `--update-startup-env` manages the root startup layout's `env` map with set/remove/clear operations. It is intentionally separate from `--update-startup` so root startup shell/command fields and environment secrets have distinct command surfaces.
- Root environment update output redacts environment variable values. Text and JSON outputs expose only sorted key names, counts, changed state, and added/updated/removed key lists so automation logs cannot accidentally print secrets.
- Root environment updates apply operations in clear, remove, then set order. Duplicate `--startup-env KEY=VALUE` entries are allowed and the last set wins, so automation can safely override an earlier value in one command.
- Clearing the root env map removes the `env` field from `terminal.json` when editing an existing file instead of writing an empty object, matching the compact root serialization style used by other root startup updates.
- `--add-startup-tab` appends exactly one root `tabs[]` entry in `terminal.json` without starting GPUI, initializing terminal UI, or opening a terminal window.
- Root startup tab append supports shell-only tabs, command-backed tabs, profile-backed tabs, titles, working directories for non-profile tabs, environment variables for command-backed tabs, and split placement with `right`, `down`, `left`, or `up`.
- Profile-backed appended tabs intentionally allow only profile, title, and split overrides; working directory, command, shell, and env remain owned by the referenced profile.
- Root startup tab append initializes a missing `terminal.json` from the standard commented startup config template, validates before writing, then reparses and revalidates the edited JSONC text before committing the file update.
- Root startup tab append preserves surrounding JSONC comments/formatting where possible through `settings_json::replace_value_in_json_text`, appending only the new root `tabs[]` item.
- Root startup tab append output redacts environment variable values. Text and JSON outputs expose only sorted env key names and counts so automation logs cannot accidentally print secrets.
- `--add-startup-tab-format` requires `--add-startup-tab` and is deliberately separate from `--update-startup-format`, `--update-startup-env-format`, `--update-profile-startup-format`, `--update-profile-env-format`, `--update-profile-format`, `--create-profile-format`, `--rename-profile-format`, `--remove-profile-format`, `--profile-visibility-format`, `--default-profile-format`, `--paths-format`, `--list-profiles-format`, `--startup-layout-format`, `--describe-startup-format`, `--validate-startup-config-format`, `--validate-keymap-format`, `--init-config-format`, and `--doctor-format`.
- Root startup tab append is a standalone config-management surface only; it does not touch terminal renderer, input, PTY, startup rendering, keymap defaults, or visual styling.
- `--update-profile-env` manages a profile's `env` map with set/remove/clear operations. It is intentionally separate from `--update-profile` and `--update-profile-startup` so metadata, startup shell/command fields, and environment secrets have distinct command surfaces.
- Profile environment update output redacts environment variable values. Text and JSON outputs expose only sorted key names, counts, changed state, and added/updated/removed key lists so automation logs cannot accidentally print secrets.
- Profile environment updates apply operations in clear, remove, then set order. Duplicate `--profile-env KEY=VALUE` entries are allowed and the last set wins, so automation can safely override an earlier value in one command.
- Clearing a profile env map removes the `env` field from `terminal.json` instead of writing an empty object, matching the existing compact profile serialization style.
- Setting a root `command` through `--update-startup` clears the root `shell`; setting a root `shell` clears the root `command`, matching the existing startup model where command-backed tabs and shell-only tabs are mutually exclusive.
- Setting a profile `command` through `--update-profile-startup` clears that profile's `shell`; setting a profile `shell` clears that profile's `command`, matching the existing startup model where command-backed tabs and shell-only tabs are mutually exclusive.
- Root startup updates read or initialize, validate, edit, reparse, and revalidate `terminal.json` at execution time, preserving JSONC comments/formatting where possible with the existing `settings_json` replacement helpers.
- Profile startup updates read, validate, edit, reparse, and revalidate `terminal.json` at execution time, preserving JSONC comments/formatting where possible with the existing `settings_json` replacement helpers.
- The standalone default keymap is tested against GPUI's registered action inventory so new bindings cannot silently reference missing actions.
- Runtime new windows use standalone `zed_terminal::NewTerminalWindow`, exposed as `ctrl-shift-n` and Window > New Window, matching Windows Terminal's `OpenNewWindow` shortcut and Zed's Windows/Linux new-window shortcut shape.
- `NewTerminalWindow` opens another standalone GPUI window through the same `open_terminal_window` path, but uses `LaunchOptions::runtime_new_window_options` so it starts with the resolved `NewTerminalTab` template only and does not replay CLI one-shot startup commands, configured startup `tabs`, CLI-appended tabs, or split placement.
- Runtime new windows still carry the resolved path options and new-tab working directory/template, so standalone config/data roots and default-directory behavior stay aligned with the current app session.
- Runtime close window uses standalone `zed_terminal::CloseTerminalWindow`, exposed as `alt-f4` on Windows and Window > Close Window, matching Windows Terminal's `closeWindow` shortcut without replacing the standalone `ctrl-shift-w` close-tab binding.
- `CloseTerminalWindow` reuses `Workspace::prepare_to_close(CloseIntent::CloseWindow)` before calling GPUI `Window::remove_window`, so close-window behavior keeps Zed's existing workspace/item close lifecycle instead of bypassing it.
- Runtime window minimize and zoom/maximize use standalone `zed_terminal::MinimizeTerminalWindow` and `zed_terminal::ZoomTerminalWindow`, exposed through the Window menu and command palette, and directly reuse GPUI's `Window::minimize_window` and `Window::zoom_window`.
- Minimize and zoom/maximize intentionally have no standalone default keybindings because they are platform window-menu actions rather than stable Windows Terminal terminal-keyboard defaults.
- Window full screen uses standalone `zed_terminal::ToggleFullScreen`, which directly calls GPUI's `Window::toggle_fullscreen` instead of depending on Zed's main application crate.
- `f11` follows Zed's Windows/Linux full-screen default and Windows Terminal's `Terminal.ToggleFullscreen`; `alt-enter` is exposed only in the Windows terminal context to match Windows Terminal without stealing Alt+Enter behavior on other platforms.
- Windows Terminal's `switchToTab` reference is applied as `ctrl-alt-1` through `ctrl-alt-8`, mapped to Zed's existing `pane::ActivateItem` action with 0-based indexes 0 through 7.
- Direct tab switching is a standalone keymap composition change only; it adds no standalone action and does not touch terminal rendering, input, or PTY behavior.
- Windows Terminal's terminal-buffer search reference is applied as `ctrl-shift-f`, mapped to Zed's existing `buffer_search::Deploy` action.
- Terminal buffer search reuses `search::BufferSearchBar`, `TerminalView`'s existing `SearchableItem` implementation, and `workspace::PaneSearchBarCallbacks`; the standalone app initializes `search::buffer_search` only and does not initialize project-wide search.
- Terminal search is a standalone composition change only; it adds no terminal renderer, input, PTY, or search algorithm fork.
- Terminal font zoom reuses Zed's existing `zed::IncreaseBufferFontSize`, `zed::DecreaseBufferFontSize`, and `zed::ResetBufferFontSize` actions plus `theme_settings` buffer font size adjustment.
- Standalone default font zoom bindings pass `{ "persist": false }`, matching Zed's session-only defaults; custom keymaps may pass `{ "persist": true }` to write the standalone `settings.json`.
- Terminal font zoom is a standalone action registration, keymap, and menu composition change only; it adds no terminal renderer, input, PTY, or font metric fork.
- Command palette support reuses Zed's existing `command_palette` crate, `command_palette::Toggle` action, and `command_palette_hooks::CommandPaletteFilter`; the standalone app initializes it before `workspace::Workspace` creation so it can register against every new workspace.
- The standalone command palette hides broad mixed namespaces such as `zed`, `workspace`, `pane`, `terminal`, `editor`, `buffer_search`, `command_palette`, and `zed_terminal`, then explicitly re-shows known terminal product action types.
- Command palette filtering is intentionally a whitelist over the terminal product surface: terminal/editor/project/AI/debug/theme/internal actions remain hidden unless they are deliberately added to the standalone app's menus, keymap, or support surface.
- Internal/test-like terminal actions such as `terminal::SearchTest` stay hidden even though official terminal actions are reused.
- `zed-terminal --describe-profile <name>` is a read-only startup profile inspection command for settings/profile UI flows. It validates `terminal.json`, accepts hidden profiles by explicit name, reports full profile and nested tab structure, and does not open a terminal window.
- Profile description output redacts environment variable values. Text and JSON outputs expose only `env_count` and sorted `env_keys`, so profile inspection cannot accidentally print secrets stored in `terminal.json`.
- Profile description intentionally requires an existing readable `terminal.json`, matching other profile management commands that operate on named profiles rather than inventing an implicit config source.

- Standalone pane resize actions call `Workspace::resize_pane`, which reuses the existing `PaneGroup::resize` flex layout logic. Horizontal resize uses the current buffer-font `m` width as one step, and vertical resize uses the current buffer line height as one step.
- Standalone pane size reset uses `zed_terminal::ResetPaneSizes`, which calls `Workspace::reset_pane_sizes` and reuses the existing `PaneGroup::reset_pane_sizes` layout behavior.
- `Reset Pane Sizes` is exposed through the Pane menu and user keymaps, but it has no standalone default keybinding because Windows Terminal does not provide a stable default binding for this operation.
- Startup directory arguments are resolved before GPUI startup, canonicalized with `dunce`, and rejected if they are not existing directories.
- `LaunchOptions` stores a full `new_terminal_tab` `LaunchTab` template for the standalone `NewTerminalTab` action used by `ctrl-shift-t` and the Shell > New Tab menu item.
- `NewTerminalTab` reuses the selected root/default-profile initial tab's working directory, command, title, env, and shell through `add_launch_tab`, preserving the same terminal creation path as configured startup tabs and profile tabs.
- CLI startup command and `--title` are one-shot overrides for the initial startup tab only; they do not replace the runtime `NewTerminalTab` template. CLI startup directory still acts as the window-level starting directory and is applied to both the initial tab and the runtime `NewTerminalTab` template.
- Runtime `NewTerminalTab` fills a missing template working directory with Zed's existing `terminal_view::default_working_directory`, preserving official terminal default-directory behavior.
- Runtime `DuplicateTerminalTab` follows Windows Terminal's `ctrl-shift-d` shortcut and first tries to duplicate the active `TerminalView`.
- `DuplicateTerminalTab` reuses Zed's existing `Project::clone_terminal` and `Terminal::clone_builder` path, which copies the active terminal's shell template, environment, terminal settings, activation script, current working directory, and custom tab title into a new center tab.
- If the active item is not a terminal, `DuplicateTerminalTab` falls back to the same standalone `LaunchTab` template used by `NewTerminalTab`.
- Duplicate tab deliberately does not clone the running child process, scrollback buffer, selection, pane layout, or PTY state. For task terminals, Zed's existing `Project::clone_terminal` behavior opens a fresh shell instead of re-running the task.
- The startup directory is also added as a visible local worktree so native Zed terminal affordances can still fall back to Zed's project-root default directory logic.
- The `-d` and `--startingDirectory` CLI shape follows Microsoft Learn's Windows Terminal command-line argument documentation.
- Startup commands must be separated with `--` so positional directories remain unambiguous.
- Startup commands are mapped to `task::SpawnInTerminal` and opened through `Project::create_terminal_task`, preserving Zed's existing shell wrapping, environment resolution, task summary, and terminal renderer.
- `terminal.json` `env` is passed through `task::SpawnInTerminal.env` for command-backed startup tabs only. Root/profile env is inherited by configured commands and CLI command tabs for the selected layout, while tab-level env overrides inherited keys.
- Shell-only startup tabs keep using Zed terminal settings and the normal shell environment. Tab-level `env` without a `command` is rejected because `Project::create_terminal_shell` does not expose a per-launch env override.
- `terminal.json` `title` initializes `TerminalView` custom titles through the existing official tab title path. Root/profile `title` names only the selected initial tab; `tabs[].title` names that configured tab. Blank titles are normalized to unset titles so dynamic terminal titles remain available.
- CLI startup titles reuse the same `LaunchTab.title` and `TerminalView` custom-title path as `terminal.json`. `--title` overrides the selected initial tab title, while `--new-tab-title` and `--new-tab-command-title` apply only to CLI-appended tabs.
- `terminal.json` `shell` accepts either a string program or an object with `program` and `args`. Root/profile `shell` is inherited by shell-only startup tabs and by the standalone `NewTerminalTab` template; `tabs[].shell` overrides it for that shell-only tab.
- Command-backed startup tabs do not inherit `shell`; they continue to run through `Project::create_terminal_task`. A configured `tabs[]` entry with both `command` and `shell` is rejected so shell selection is not silently ignored.
- `terminal.json` `tabs[].split` accepts `right`, `down`, `left`, or `up`. When present, that configured startup tab opens as a split pane instead of as another tab in the active pane.
- `terminal.json` `tabs[].profile` resolves a named profile's initial tab only. It does not replay that profile's own `tabs` list, so profile references do not introduce recursive startup layouts.
- `terminal.json` profile tab references may override only `title` and `split`. Mixing `profile` with `working_directory`, `command`, `shell`, or `env` is rejected so profile references do not need unclear merge semantics.
- Startup profile tab references may target hidden profiles because `terminal.json` is an explicit configuration surface. Hidden profiles remain hidden from Shell menus and command palette entries.
- Startup split panes are created sequentially after the initial tab so split placement follows `terminal.json` order. CLI-appended `--new-tab` and `--new-tab-command` entries always remain normal tabs and do not inherit configured split placement.
- Startup split panes reuse `TerminalPanel::split_center_terminal_with_custom_title`, `Workspace::split_item`, `TerminalView::new_with_custom_title`, `Project::create_terminal_shell`, `Project::create_terminal_shell_with_shell`, and `Project::create_terminal_task`; no terminal renderer or input handling is forked.
- Startup tabs are modeled as `LaunchTab` values. The first tab supports the existing startup command path; repeated `--new-tab` / `--tab` entries create shell tabs with their own working directories, repeated `--new-tab-profile` / `--tab-profile` entries create profile-derived tabs, and repeated `--new-tab-command` / `--tab-command` entries create command tabs.
- CLI-appended startup tabs keep the existing category ordering instead of preserving raw argument interleaving: configured tabs first, then CLI directory tabs, then CLI profile tabs, then CLI command tabs.
- Additional command tab strings are parsed with `shlex`, then mapped to `task::SpawnInTerminal` and opened through `Project::create_terminal_task`.
- Additional command tab working directories are supplied with repeated `--new-tab-command-directory` / `--tab-command-directory` entries. They map to command tabs by index; fewer directories leave later command tabs on the project default working directory, while extra directories without matching commands are rejected.
- Additional CLI tab titles are supplied with repeated `--new-tab-title` / `--tab-title`, `--new-tab-profile-title` / `--tab-profile-title`, and `--new-tab-command-title` / `--tab-command-title` entries. They map within their own shell-tab, profile-tab, or command-tab category by index; fewer titles leave later tabs on dynamic titles, while extra titles without matching tabs are rejected.
- Additional CLI profile tab splits are supplied with repeated `--new-tab-profile-split` / `--tab-profile-split` entries and map to profile tabs by index. Fewer split entries leave later profile tabs as normal tabs, while extra split entries without matching profile tabs are rejected.
- Startup tab directories and the runtime `NewTerminalTab` template directory are registered as local worktrees before terminal creation so Zed terminal affordances still resolve project-root defaults consistently.
- `terminal.json` supplies startup layout only. If `--profile <name>` is present, that named profile is selected. Otherwise `default_profile` is selected when present. If neither is present, the root-level startup layout is selected.
- Profile metadata is surfaced by `--list-profiles`, by the Shell profile submenus, and by dynamic command palette profile entries. Runtime profile tabs and profile splits still reuse existing `LaunchTab`, `TerminalPanel`, `Project::create_terminal_shell`, and `Project::create_terminal_task` paths.
- Runtime profile tab and split creation open only the selected profile's initial tab. They do not replay the profile's configured `tabs` list after startup.
- Runtime profile splits use `zed_terminal::NewTerminalSplitWithProfile`, override only `LaunchTab.split`, and then reuse `TerminalPanel::split_center_terminal_with_custom_title`; right/down/left/up split directions share one profile split direction table so Shell menu and command palette exposure stay aligned. No terminal renderer or input behavior is forked.
- Hidden profiles are excluded from Shell profile submenus, but may still be invoked directly through `zed_terminal::NewTerminalTabWithProfile` or `zed_terminal::NewTerminalSplitWithProfile` from a user keymap.
- The app watches `terminal.json` and refreshes the Shell profile submenu when startup profile configuration changes. Parse failures are logged and leave the basic Shell menu usable.
- `--validate-startup-config` reads and validates `terminal.json`, prints the validated config path plus layout/tab counts, and exits without starting GPUI or opening a terminal window.
- `--validate-startup-config` defaults to the stable human-readable text report for compatibility.
- `--validate-startup-config --validate-startup-config-format json` uses the same `TerminalStartupConfigValidationReport` data to print parseable JSON with config path, status, layout count, and tab count for release scripts and settings UI automation.
- `--validate-startup-config-format` requires `--validate-startup-config` and is deliberately separate from `--paths-format`, `--list-profiles-format`, `--startup-layout-format`, and `--doctor-format`, so startup config validation does not inherit unrelated output-format flags.
- Startup config validation checks the root layout, every named profile including hidden profiles, `default_profile` references, profile tab references, configured working directories, command parsing, shell parsing, and unsupported `env`/`shell`/profile field combinations by reusing the same `LaunchTab` resolution path as startup.
- `--list-profiles` reads `terminal.json`, prints visible profile metadata, and exits without starting GPUI or resolving the selected startup layout. `--all-profiles` includes profiles marked `hidden`.
- `--list-profiles` defaults to the stable human-readable text report. `--list-profiles-format json` uses the same `TerminalStartupProfileListReport` fields to print parseable JSON with config path, include-hidden state, counts, and profile metadata for future settings UI and automation.
- `--list-profiles-format` requires `--list-profiles` and is deliberately separate from `--doctor-format`, `--paths-format`, and the doctor `--format` alias.
- `--list-profiles` conflicts with startup-only arguments such as `--profile`, startup directories, startup commands, and additional startup tabs so those arguments are not silently ignored.
- CLI initial directory and startup command override the selected startup layout's initial tab fields, while CLI `--new-tab`, `--new-tab-profile`, and `--new-tab-command` entries append after configured tabs.
- `--no-startup-config` ignores `terminal.json` entirely and conflicts with `--profile` and `--new-tab-profile`.
- `terminal.json` is parsed with Zed's JSON-with-comments parser and uses `serde(deny_unknown_fields)` so misspelled startup config keys fail early instead of being silently ignored.
- Configured command strings use the same `shlex` parser as `--new-tab-command`.
- Configured working directories use the same resolver as CLI directories. Use absolute paths or `~` in long-lived startup config for stable launches from shortcuts.

## Known Risks

- The app still depends on a large subset of Zed workspace initialization; future work should reduce accidental editor-only surface without breaking terminal behavior.
- Visual smoke coverage now catches blank-window/startup screenshot regressions, but there is still no automated pixel-baseline parity test for official Zed terminal cell metrics, colors, and tab chrome.

- Extend `terminal.json` profile metadata toward richer picker/settings presentation.
