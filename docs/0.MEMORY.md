# Zed Terminal Memory

This file records durable project context for the standalone `zed_terminal` app.

## Product Direction

- Build a standalone terminal application that feels like a product, not a demo.
- Preserve the official Zed terminal rendering and component style.
- Iterate primarily by composing Zed crates from a new `crates/zed_terminal` binary crate.
- Keep changes to existing Zed crates minimal and only expose APIs when composition requires it.
- Use Windows Terminal as the reference for tab, split, settings, and shortcut expectations.

## Current Architecture

- `crates/zed_terminal` is a standalone binary crate with binary name `zed-terminal`.
- The app initializes a lightweight subset of Zed services and opens one GPUI window.
- `workspace::Workspace` provides the center pane, tab strip, split panes, focus, and item lifecycle.
- `terminal_view::TerminalPanel::add_center_terminal` creates terminal tabs backed by Zed's existing terminal stack.
- `terminal_view::TerminalPanel::add_center_terminal_with_custom_title` is the standalone startup path for titled tabs and initializes the same `TerminalView` custom title state used by official Zed terminal tab renaming.
- `terminal_view::TerminalPanel::split_center_terminal_with_custom_title` is the narrow standalone startup path for configured split panes and still creates the same official `TerminalView` before handing it to `workspace::Workspace::split_item`.
- `project::Project::create_terminal_shell_with_shell` is the standalone startup path for configured shell-only tabs and keeps them on the same normal terminal shell lifecycle as Zed terminals.
- `terminal`, `terminal_view`, `workspace`, `command_palette`, `search`, `ui`, settings, themes, and keymaps are reused instead of forked.
- Standalone command palette filtering uses `command_palette_hooks::CommandPaletteFilter`; it hides broad Zed/editor/project namespaces and explicitly re-shows known terminal product actions.
- Standalone terminal buffer search initializes Zed's `search::buffer_search` surface, registers `workspace::PaneSearchBarCallbacks`, and mounts `search::BufferSearchBar` into each terminal pane toolbar before `terminal_view` creates terminal panes.
- `crates/paths` exposes custom data/config directory hooks so `zed-terminal` can be a standalone product without changing normal Zed paths.
- By default, `zed-terminal` uses independent config/data/log roots named `Zed Terminal` / `zed-terminal`, with `--user-data-dir` and `--config-dir` overrides for smoke tests and custom roots.
- `zed-terminal --portable` uses `data/` and `config/` directories next to the running `zed-terminal` binary. This is the release-package portable launch path and is intentionally supported by the same path resolution model as every no-window diagnostic/config command.
- The default terminal keymap lives at `assets/keymaps/zed-terminal.json` and is loaded through `settings::KeymapFile` before user keymap overrides.
- Standalone startup layout is configured by `terminal.json` in the active terminal config directory. It is intentionally separate from Zed's normal `settings.json`, so Zed settings can keep owning themes, fonts, and terminal renderer behavior.
- The first-run `terminal.json` template stays behaviorally empty but now includes commented guidance for validation/discovery commands, startup paths, command/shell/env semantics, split placement, profile references, default profiles, and a complete commented example layout.
- Standalone CLI handling is split into explicit early path/version commands plus `ListProfiles`, `DescribeProfile`, `DescribeStartup`, `SetDefaultProfile`, `ClearDefaultProfile`, `PrintStartupLayout`, `UpdateStartup`, `UpdateStartupEnv`, `AddStartupTab`, `RemoveStartupTab`, `MoveStartupTab`, `ValidateSettings`, `ValidateStartupConfig`, `PrintStartupConfigSchema`, `PrintDefaultKeymap`, `InitConfig`, `Doctor`, `ValidateKeymap`, and `Launch` modes so discovery, configuration edits, initialization, diagnostics, and validation commands do not accidentally validate unrelated startup state or launch terminal windows.
- `zed-terminal --paths` is an early non-window command, intentionally parsed before the main clap CLI, so package/release validation can inspect deeply nested custom and portable paths without traversing the full launch/config command graph.
- `zed-terminal --paths --paths-format json` includes a `mode` field (`default`, `custom`, or `portable`) so support-info, release-package smoke, and automation can prove which path policy produced the reported directories.
- `zed-terminal --paths` reports `settings_schema_file` next to `settings_file`, `terminal.schema.json`, `keymap.schema.json`, and `default-keymap.json`, so editor tooling and support automation can discover the generated settings schema location without opening the app.
- `zed-terminal --version-info` is an early non-window command, intentionally parsed before the main clap CLI, and `--version-info --version-info-format json` reports app name, binary name, package name, version, target OS/architecture, and debug-assertion mode for release/package traceability.
- Main clap help generation and normal `Cli::try_parse_from` run on a dedicated larger-stack parser thread, then command execution returns to the main thread. This keeps Windows debug/package validation stable for deeply nested path arguments without moving GPUI/window startup off the main thread.
- Startup profile transfer options are parsed before the main clap CLI as a narrow early path for `--export-profile` and `--import-profile`, avoiding further growth of the derived command graph while preserving the same standalone path resolution and config mutation helpers.
- Support bundle generation is parsed before the main clap CLI as a narrow early no-window path for `--support-bundle --support-bundle-dir <DIR>`, so support artifacts can be generated even when startup config is broken and without growing the normal launch command graph.
- Because path inspection, profile transfer, support bundle, startup config file, keymap file, and version metadata options intentionally stay out of the main clap argument graph or use hidden compatibility-only clap flags, `Cli` documents them through static `after_help` text, and the release gate asserts that `zed-terminal --help` keeps them discoverable.

## Rendering Parity Requirements

The app must keep these startup steps aligned with Zed before terminal views are created:

- `gpui_platform::application().with_assets(Assets)`
- `Assets.load_fonts(cx)` for embedded `.ZedMono` and `.ZedSans`
- `theme_settings::init(theme::LoadThemes::All(Box::new(Assets)), cx)`
- load and watch user themes from `paths::themes_dir()`
- initialize and watch settings files before first terminal render
- synchronize `WorkspaceSettings::text_rendering_mode`
- apply the active theme's window background appearance

Skipping these steps breaks font metrics and theme colors, which makes the standalone terminal diverge from the official Zed terminal.
