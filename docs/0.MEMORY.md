# Zed Terminal Memory

This file records durable project context for the standalone `zed_terminal` app.

## Product Direction

- Build a standalone terminal application that feels like a product, not a demo.
- Preserve the official Zed terminal rendering and component style.
- Iterate primarily by composing Zed crates from a new `crates/zed_terminal` binary crate.
- Keep changes to existing Zed crates minimal and only expose APIs when composition requires it.
- Use Windows Terminal as the reference for tab, split, settings, and shortcut expectations.

## Current Architecture

- `crates/zed_terminal` is a standalone binary crate with binary name `zed-terminal`.
- The app initializes a lightweight subset of Zed services and opens one GPUI window.
- `workspace::Workspace` provides the center pane, tab strip, split panes, focus, and item lifecycle.
- `terminal_view::TerminalPanel::add_center_terminal` creates terminal tabs backed by Zed's existing terminal stack.
- `terminal_view::TerminalPanel::add_center_terminal_with_custom_title` is the standalone startup path for titled tabs and initializes the same `TerminalView` custom title state used by official Zed terminal tab renaming.
- `terminal_view::TerminalPanel::split_center_terminal_with_custom_title` is the narrow standalone startup path for configured split panes and still creates the same official `TerminalView` before handing it to `workspace::Workspace::split_item`.
- `project::Project::create_terminal_shell_with_shell` is the standalone startup path for configured shell-only tabs and keeps them on the same normal terminal shell lifecycle as Zed terminals.
- `terminal`, `terminal_view`, `workspace`, `search`, `ui`, settings, themes, and keymaps are reused instead of forked.
- Standalone terminal buffer search initializes Zed's `search::buffer_search` surface, registers `workspace::PaneSearchBarCallbacks`, and mounts `search::BufferSearchBar` into each terminal pane toolbar before `terminal_view` creates terminal panes.
- `crates/paths` exposes custom data/config directory hooks so `zed-terminal` can be a standalone product without changing normal Zed paths.
- By default, `zed-terminal` uses independent config/data/log roots named `Zed Terminal` / `zed-terminal`, with `--user-data-dir` and `--config-dir` overrides for smoke tests and portable launches.
- The default terminal keymap lives at `assets/keymaps/zed-terminal.json` and is loaded through `settings::KeymapFile` before user keymap overrides.
- Standalone startup layout is configured by `terminal.json` in the active terminal config directory. It is intentionally separate from Zed's normal `settings.json`, so Zed settings can keep owning themes, fonts, and terminal renderer behavior.
- Standalone CLI handling is split into explicit `PrintPaths`, `ListProfiles`, `SetDefaultProfile`, `ClearDefaultProfile`, `PrintStartupLayout`, `ValidateStartupConfig`, `PrintStartupConfigSchema`, `InitConfig`, `Doctor`, `ValidateKeymap`, and `Launch` modes so discovery, configuration edits, initialization, diagnostics, and validation commands do not accidentally validate unrelated startup state or launch terminal windows.

## Rendering Parity Requirements

The app must keep these startup steps aligned with Zed before terminal views are created:

- `gpui_platform::application().with_assets(Assets)`
- `Assets.load_fonts(cx)` for embedded `.ZedMono` and `.ZedSans`
- `theme_settings::init(theme::LoadThemes::All(Box::new(Assets)), cx)`
- load and watch user themes from `paths::themes_dir()`
- initialize and watch settings files before first terminal render
- synchronize `WorkspaceSettings::text_rendering_mode`
- apply the active theme's window background appearance

Skipping these steps breaks font metrics and theme colors, which makes the standalone terminal diverge from the official Zed terminal.

## Implemented Product Surface

- One standalone terminal window titled `Zed Terminal`.
- New terminal tab: `ctrl-shift-t`.
- Close tab: `ctrl-shift-w`.
- Next/previous tab: `ctrl-tab` / `ctrl-shift-tab`.
- Direct tab switching: `ctrl-alt-1` through `ctrl-alt-8` activates tabs 1 through 8.
- Split right/down: `ctrl-shift-5` / `alt-shift-plus`.
- Windows Terminal-style split aliases: `alt-shift-d` for split right and `alt-shift-minus` for split down.
- Toggle focused pane zoom: `shift-escape`.
- Windows Terminal-style pane focus on Windows: `alt-left`, `alt-right`, `alt-up`, and `alt-down`.
- Windows Terminal-style pane resize on Windows: `alt-shift-left`, `alt-shift-right`, `alt-shift-up`, and `alt-shift-down`.
- Select all terminal text: `ctrl-shift-a`.
- Find in terminal buffer: `ctrl-shift-f`.
- Scroll aliases: `ctrl-shift-up/down`, `ctrl-shift-pageup/pagedown`, and `ctrl-shift-home/end`.
- Open settings file: `ctrl-,`.
- Open startup config file from the app menu.
- Open keymap file from the app menu.
- Menu entries for settings, keymap, config directory, logs directory, tab actions, bulk tab close actions, terminal operations, pane split actions, pane focus actions, pane cycling, pane zoom, pane resize, and pane size reset.
- Shell menu can move the active tab left or right.
- The Terminal menu exposes official Zed terminal actions for find, copy, paste, paste text, select all, clear, vi mode, character palette, scrolling, task rerun, and terminal rename.
- Shell menu includes `New Tab With Profile`, `Split Right With Profile`, `Split Down With Profile`, and `Set Default Profile` for visible startup profiles from `terminal.json`, plus `Clear Default Profile` for returning startup to the root layout.
- User keymaps can invoke `zed_terminal::NewTerminalTabWithProfile` with `{ "profile": "<name>" }`.
- User keymaps can invoke `zed_terminal::NewTerminalSplitWithProfile` with `{ "profile": "<name>", "direction": "right" }`, where `direction` accepts `right`, `down`, `left`, or `up`.
- User keymaps can invoke `zed_terminal::SetDefaultStartupProfile` with `{ "profile": "<name>" }`.
- User keymaps can invoke `zed_terminal::ClearDefaultStartupProfile`.
- User keymaps can invoke `zed_terminal::ResetPaneSizes`.
- Keymap validation option:
  - `zed-terminal --validate-keymap`
  - Validates the bundled standalone default keymap and the active user `keymap.json` without opening a terminal window.
- Startup config schema option:
  - `zed-terminal --print-startup-config-schema`
  - Prints the JSON Schema for `terminal.json` without opening a terminal window.
- Config initialization option:
  - `zed-terminal --init-config`
  - Creates missing `settings.json`, global settings, `keymap.json`, and `terminal.json` without opening a terminal window.
- Doctor diagnostics option:
  - `zed-terminal --doctor`
  - Runs read-only diagnostics for standalone paths, config files, `terminal.json`, and keymaps without opening a terminal window.
- Path inspection and override options:
  - `zed-terminal --paths`
  - `zed-terminal --user-data-dir <directory>`
  - `zed-terminal --config-dir <directory>`
- Startup config options:
  - `zed-terminal --no-startup-config`
  - `zed-terminal --profile <name>`
  - `zed-terminal --print-startup-layout`
  - `zed-terminal --set-default-profile <name>`
  - `zed-terminal --clear-default-profile`
  - `zed-terminal --validate-startup-config`
  - `zed-terminal --list-profiles`
  - `zed-terminal --list-profiles --all-profiles`
  - The startup config file is reported by `zed-terminal --paths` as `startup_config_file`.
  - `terminal.json` supports root-level `working_directory`, `command`, and `tabs`.
  - `terminal.json` supports root/profile/tab `title` values for startup tab labels.
  - `terminal.json` supports root/profile/tab `shell` values for shell-only startup tabs.
  - `terminal.json` supports `tabs[].split` with `right`, `down`, `left`, or `up` for startup split panes.
  - `terminal.json` also supports root/profile/tab `env` maps for command-backed startup tabs.
  - `terminal.json` also supports `default_profile` and named `profiles`, where each profile has its own `working_directory`, `command`, `title`, `shell`, `env`, `tabs`, and discovery metadata.
  - Profile metadata fields are `display_name`, `description`, `icon`, `color`, and `hidden`.
- Startup working directory options:
  - `zed-terminal -d <directory>`
  - `zed-terminal --working-directory <directory>`
  - `zed-terminal --cwd <directory>`
  - `zed-terminal --starting-directory <directory>`
  - `zed-terminal --startingDirectory <directory>`
  - `zed-terminal <directory>`
- Startup command options:
  - `zed-terminal -- <command> [args...]`
  - `zed-terminal <directory> -- <command> [args...]`
  - `zed-terminal -d <directory> -- <command> [args...]`
  - `zed-terminal --title <title>`
  - The title option overrides the initial startup tab label.
- Additional startup tab options:
  - `zed-terminal --new-tab <directory>`
  - `zed-terminal --tab <directory>`
  - These options can be repeated and create extra shell tabs at startup.
  - `zed-terminal --new-tab-title <title>`
  - `zed-terminal --tab-title <title>`
  - Shell tab title options are mapped to `--new-tab` / `--tab` entries by index.
  - `zed-terminal --new-tab-command "<command> [args...]"`
  - `zed-terminal --tab-command "<command> [args...]"`
  - Command tab options can be repeated and create extra task-backed startup tabs.
  - `zed-terminal --new-tab-command-directory <directory>`
  - `zed-terminal --tab-command-directory <directory>`
  - Command tab directory options are mapped to command-backed startup tabs by index.
  - `zed-terminal --new-tab-command-title <title>`
  - `zed-terminal --tab-command-title <title>`
  - Command tab title options are mapped to command-backed startup tabs by index.

## Verification Commands

Use the stable toolchain for this crate:

```sh
cargo +stable fmt --package zed_terminal
cargo +stable test -p zed_terminal --bin zed-terminal
cargo +stable check -p zed_terminal
cargo +stable build -p zed_terminal --bin zed-terminal
```

When manually checking the app on Windows, stop any running `zed-terminal.exe` before rebuilding or the linker may fail to replace the executable.

## Current Decisions

- The standalone app no longer shares normal Zed config/data paths by default.
- The settings and keymap actions open terminal-specific `settings.json` and `keymap.json` under the active terminal config directory.
- Product support entries open the config and logs directories using GPUI's platform `open_with_system` API.
- `ctrl-j` is intentionally left unbound in the standalone default keymap so the terminal receives LF input.
- The standalone default keymap is tested against GPUI's registered action inventory so new bindings cannot silently reference missing actions.
- Windows Terminal's `switchToTab` reference is applied as `ctrl-alt-1` through `ctrl-alt-8`, mapped to Zed's existing `pane::ActivateItem` action with 0-based indexes 0 through 7.
- Direct tab switching is a standalone keymap composition change only; it adds no standalone action and does not touch terminal rendering, input, or PTY behavior.
- Windows Terminal's terminal-buffer search reference is applied as `ctrl-shift-f`, mapped to Zed's existing `buffer_search::Deploy` action.
- Terminal buffer search reuses `search::BufferSearchBar`, `TerminalView`'s existing `SearchableItem` implementation, and `workspace::PaneSearchBarCallbacks`; the standalone app initializes `search::buffer_search` only and does not initialize project-wide search.
- Terminal search is a standalone composition change only; it adds no terminal renderer, input, PTY, or search algorithm fork.
- `--validate-keymap` validates `assets/keymaps/zed-terminal.json` through `KeymapFile::load_asset` and validates the active user `keymap.json` through `settings::KeymapFile::load`, so action names, contexts, action params, and keystrokes use Zed's real keymap loader.
- Keymap validation is independent from `terminal.json`; broken startup config must not block `zed-terminal --validate-keymap`.
- Missing user `keymap.json` is validated with `settings::initial_keymap_content()` and reported as `user_keymap_source: initial` instead of creating a config file.
- Keymap validation runs a minimal GPUI application callback because keymap loading needs `gpui::App`, but it does not initialize terminal UI or open a terminal window.
- `--print-startup-config-schema` derives its output from the same `TerminalStartupConfig` structs used to parse `terminal.json`, so the public configuration contract stays tied to runtime behavior.
- Startup config schema printing is independent from the active `terminal.json`; broken user startup config must not block schema discovery.
- Startup config schema printing does not start GPUI, initialize terminal UI, or open a terminal window.
- `--init-config` creates only missing standalone config files and reports `created` or `existing` for each file; it never overwrites existing files.
- Runtime first-run config creation and menu-open file creation reuse the same initialization helper as `--init-config`.
- Config initialization is independent from the active `terminal.json`; broken startup config must not block `zed-terminal --init-config`.
- `--doctor` is read-only: it reports missing files and directories as `missing` without creating them, and reports parse/validation/path-kind failures as `error`.
- Missing standalone config files are non-fatal in `--doctor` because the runtime can use initial content and users can run `--init-config` when they want files materialized.
- `--doctor` reuses `TerminalStartupConfig::validate` and the real `settings::KeymapFile` loaders so diagnostics stay aligned with launch, startup validation, and keymap validation behavior.
- `--doctor` starts the minimal GPUI application callback needed for keymap loading, but it does not initialize terminal UI or open a terminal window.
- `--print-startup-layout` prints the resolved `LaunchOptions` startup tabs without installing custom Zed paths, starting GPUI, initializing terminal UI, or opening a terminal window.
- Startup layout printing reuses the same `LaunchOptions::from_cli_parts` resolution path as launch, so `terminal.json`, profile selection, `--no-startup-config`, CLI initial overrides, and CLI-appended tabs are previewed with launch semantics.
- Startup layout printing reports the runtime `NewTerminalTab` template plus each startup tab's command, shell, title, working directory, placement, tab kind, and env variable counts, but does not print environment variable names or values.
- `--set-default-profile <name>` updates the top-level `default_profile` field in `terminal.json` without starting GPUI, initializing terminal UI, or opening a terminal window.
- Default profile updates trim the profile name, reject blank or missing profiles, validate the updated `terminal.json`, and preserve surrounding JSONC comments/formatting through `settings_json::replace_value_in_json_text`.
- The Shell > Set Default Profile submenu uses the same `SetDefaultStartupProfile` action and `terminal.json` update helper as the CLI. Visible profiles are shown in the menu; hidden profiles may still be set directly through CLI or user keymaps.
- `--clear-default-profile` writes the top-level `default_profile` field as `null` in `terminal.json` without starting GPUI, initializing terminal UI, or opening a terminal window.
- Clearing the default profile preserves surrounding JSONC comments/formatting through `settings_json::replace_value_in_json_text`, succeeds as an unchanged no-op when `terminal.json` is missing, and does not create the file in that case.
- Clearing the default profile can repair a broken `default_profile` reference because validation runs after setting the field to `None`; other invalid layout/profile errors still fail before writing.
- The Shell > Clear Default Profile menu entry uses the same `ClearDefaultStartupProfile` action and `terminal.json` update helper as the CLI.
- Shell menu bulk tab close operations reuse existing Zed pane actions: `Close Other Tabs` uses `pane::CloseOtherItems`, `Close Tabs to the Right` uses `pane::CloseItemsToTheRight`, `Close Tabs to the Left` uses `pane::CloseItemsToTheLeft`, and `Close All Tabs` uses `pane::CloseAllItems`.
- Shell menu tab reordering reuses existing Zed pane actions: `Move Tab Left` uses `pane::SwapItemLeft`, and `Move Tab Right` uses `pane::SwapItemRight`.
- Windows Terminal's `moveTab` reference is applied through menu actions only for now; no standalone default keybinding is added because the Zed default `ctrl-shift-pageup/pagedown` shape conflicts with standalone terminal scroll aliases.
- Terminal menu operations reuse existing `terminal`, `terminal_view`, and `editor` actions; no terminal rendering or input handling is forked.
- Pane menu operations and pane focus keybindings reuse existing `workspace` and `pane` actions handled by Zed workspace/terminal panel code; no standalone pane tree or renderer behavior is forked.
- The Windows Terminal pane keyboard reference is applied where the existing Zed action surface is semantically equivalent: `Alt+Arrow` moves pane focus on Windows, and `Alt+Shift+Arrow` resizes split panes through standalone `zed_terminal::ResizePane*` actions.
- Standalone pane resize actions call `Workspace::resize_pane`, which reuses the existing `PaneGroup::resize` flex layout logic. Horizontal resize uses the current buffer-font `m` width as one step, and vertical resize uses the current buffer line height as one step.
- Standalone pane size reset uses `zed_terminal::ResetPaneSizes`, which calls `Workspace::reset_pane_sizes` and reuses the existing `PaneGroup::reset_pane_sizes` layout behavior.
- `Reset Pane Sizes` is exposed through the Pane menu and user keymaps, but it has no standalone default keybinding because Windows Terminal does not provide a stable default binding for this operation.
- Startup directory arguments are resolved before GPUI startup, canonicalized with `dunce`, and rejected if they are not existing directories.
- `LaunchOptions` stores a full `new_terminal_tab` `LaunchTab` template for the standalone `NewTerminalTab` action used by `ctrl-shift-t` and the Shell > New Tab menu item.
- `NewTerminalTab` reuses the selected root/default-profile initial tab's working directory, command, title, env, and shell through `add_launch_tab`, preserving the same terminal creation path as configured startup tabs and profile tabs.
- CLI startup command and `--title` are one-shot overrides for the initial startup tab only; they do not replace the runtime `NewTerminalTab` template. CLI startup directory still acts as the window-level starting directory and is applied to both the initial tab and the runtime `NewTerminalTab` template.
- Runtime `NewTerminalTab` fills a missing template working directory with Zed's existing `terminal_view::default_working_directory`, preserving official terminal default-directory behavior.
- The startup directory is also added as a visible local worktree so native Zed terminal affordances can still fall back to Zed's project-root default directory logic.
- The `-d` and `--startingDirectory` CLI shape follows Microsoft Learn's Windows Terminal command-line argument documentation.
- Startup commands must be separated with `--` so positional directories remain unambiguous.
- Startup commands are mapped to `task::SpawnInTerminal` and opened through `Project::create_terminal_task`, preserving Zed's existing shell wrapping, environment resolution, task summary, and terminal renderer.
- `terminal.json` `env` is passed through `task::SpawnInTerminal.env` for command-backed startup tabs only. Root/profile env is inherited by configured commands and CLI command tabs for the selected layout, while tab-level env overrides inherited keys.
- Shell-only startup tabs keep using Zed terminal settings and the normal shell environment. Tab-level `env` without a `command` is rejected because `Project::create_terminal_shell` does not expose a per-launch env override.
- `terminal.json` `title` initializes `TerminalView` custom titles through the existing official tab title path. Root/profile `title` names only the selected initial tab; `tabs[].title` names that configured tab. Blank titles are normalized to unset titles so dynamic terminal titles remain available.
- CLI startup titles reuse the same `LaunchTab.title` and `TerminalView` custom-title path as `terminal.json`. `--title` overrides the selected initial tab title, while `--new-tab-title` and `--new-tab-command-title` apply only to CLI-appended tabs.
- `terminal.json` `shell` accepts either a string program or an object with `program` and `args`. Root/profile `shell` is inherited by shell-only startup tabs and by the standalone `NewTerminalTab` template; `tabs[].shell` overrides it for that shell-only tab.
- Command-backed startup tabs do not inherit `shell`; they continue to run through `Project::create_terminal_task`. A configured `tabs[]` entry with both `command` and `shell` is rejected so shell selection is not silently ignored.
- `terminal.json` `tabs[].split` accepts `right`, `down`, `left`, or `up`. When present, that configured startup tab opens as a split pane instead of as another tab in the active pane.
- Startup split panes are created sequentially after the initial tab so split placement follows `terminal.json` order. CLI-appended `--new-tab` and `--new-tab-command` entries always remain normal tabs and do not inherit configured split placement.
- Startup split panes reuse `TerminalPanel::split_center_terminal_with_custom_title`, `Workspace::split_item`, `TerminalView::new_with_custom_title`, `Project::create_terminal_shell`, `Project::create_terminal_shell_with_shell`, and `Project::create_terminal_task`; no terminal renderer or input handling is forked.
- Startup tabs are modeled as `LaunchTab` values. The first tab supports the existing startup command path; repeated `--new-tab` / `--tab` entries create shell tabs with their own working directories, while repeated `--new-tab-command` / `--tab-command` entries create command tabs.
- Additional command tab strings are parsed with `shlex`, then mapped to `task::SpawnInTerminal` and opened through `Project::create_terminal_task`.
- Additional command tab working directories are supplied with repeated `--new-tab-command-directory` / `--tab-command-directory` entries. They map to command tabs by index; fewer directories leave later command tabs on the project default working directory, while extra directories without matching commands are rejected.
- Additional CLI tab titles are supplied with repeated `--new-tab-title` / `--tab-title` and `--new-tab-command-title` / `--tab-command-title` entries. They map within their own shell-tab or command-tab category by index; fewer titles leave later tabs on dynamic titles, while extra titles without matching tabs are rejected.
- Startup tab directories and the runtime `NewTerminalTab` template directory are registered as local worktrees before terminal creation so Zed terminal affordances still resolve project-root defaults consistently.
- `terminal.json` supplies startup layout only. If `--profile <name>` is present, that named profile is selected. Otherwise `default_profile` is selected when present. If neither is present, the root-level startup layout is selected.
- Profile metadata is surfaced by `--list-profiles` and by the Shell profile submenus. Runtime profile tabs and profile splits still reuse existing `LaunchTab`, `TerminalPanel`, `Project::create_terminal_shell`, and `Project::create_terminal_task` paths.
- Runtime profile tab and split creation open only the selected profile's initial tab. They do not replay the profile's configured `tabs` list after startup.
- Runtime profile splits use `zed_terminal::NewTerminalSplitWithProfile`, override only `LaunchTab.split`, and then reuse `TerminalPanel::split_center_terminal_with_custom_title`; no terminal renderer or input behavior is forked.
- Hidden profiles are excluded from Shell profile submenus, but may still be invoked directly through `zed_terminal::NewTerminalTabWithProfile` or `zed_terminal::NewTerminalSplitWithProfile` from a user keymap.
- The app watches `terminal.json` and refreshes the Shell profile submenu when startup profile configuration changes. Parse failures are logged and leave the basic Shell menu usable.
- `--validate-startup-config` reads and validates `terminal.json`, prints the validated config path plus layout/tab counts, and exits without starting GPUI or opening a terminal window.
- Startup config validation checks the root layout, every named profile including hidden profiles, `default_profile` references, configured working directories, command parsing, shell parsing, and unsupported `env`/`shell` combinations by reusing the same `LaunchTab` resolution path as startup.
- `--list-profiles` reads `terminal.json`, prints visible profile metadata, and exits without starting GPUI or resolving the selected startup layout. `--all-profiles` includes profiles marked `hidden`.
- `--list-profiles` conflicts with startup-only arguments such as `--profile`, startup directories, startup commands, and additional startup tabs so those arguments are not silently ignored.
- CLI initial directory and startup command override the selected startup layout's initial tab fields, while CLI `--new-tab` and `--new-tab-command` entries append after configured tabs.
- `--no-startup-config` ignores `terminal.json` entirely and conflicts with `--profile`.
- `terminal.json` is parsed with Zed's JSON-with-comments parser and uses `serde(deny_unknown_fields)` so misspelled startup config keys fail early instead of being silently ignored.
- Configured command strings use the same `shlex` parser as `--new-tab-command`.
- Configured working directories use the same resolver as CLI directories. Use absolute paths or `~` in long-lived startup config for stable launches from shortcuts.

## Known Risks

- The app still depends on a large subset of Zed workspace initialization; future work should reduce accidental editor-only surface without breaking terminal behavior.
- There is no automated visual parity test yet for terminal cell metrics, colors, and tab chrome.

## Next Priorities

- Add a richer profile picker/settings UI on top of the current Shell profile submenu and parameterized action.
- Extend startup layout toward richer Windows Terminal concepts such as nested split pane trees and an explicit action-chain grammar if the current flat split model becomes too limited.
- Extend `terminal.json` profile metadata toward richer picker/settings presentation.
- Add product-grade first-run/error states for shell spawn failures.
- Build a repeatable manual or automated visual verification path for release checkpoints.
